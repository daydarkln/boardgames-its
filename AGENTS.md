# AGENTS.md

## Контекст продукта

Мы разрабатываем веб-сервис для объединения настольного игрового сообщества города.

Основная идея: в одном месте собрать людей, места и события, связанные с настольными играми, НРИ и мафией.

Сервис должен помогать пользователям:

- находить места, где можно поиграть;
- находить ближайшие игровые встречи;
- записываться на игры;
- создавать свои игровые встречи;
- искать игроков;
- собирать группы;
- отдельно фильтровать направления:
  - настольные игры;
  - НРИ;
  - мафия.

Продукт должен ощущаться не как сухая афиша или админка, а как живая городская платформа для игроков.

## Ключевая цель MVP

Сделать рабочее приложение, где пользователь может:

1. Зайти на главную страницу.
2. Понять, что это сервис для поиска игр, мест и игроков.
3. Посмотреть ближайшие игры.
4. Найти площадку/клуб.
5. Зарегистрироваться или войти.
6. Записаться на игру.
7. Создать свою игру.
8. Посмотреть свои игры и записи в личном кабинете.

## Целевая аудитория

### Игроки

Люди, которые хотят найти компанию для игры.

Им важно:

- быстро понять, где и когда можно поиграть;
- найти игру по интересам;
- увидеть количество свободных мест;
- записаться без лишней переписки;
- понять уровень игры: новичкам можно или нет.

### Организаторы

Люди, которые собирают игры.

Им важно:

- быстро создать игровую встречу;
- указать место, дату, время и количество мест;
- видеть список записавшихся;
- управлять статусом игры;
- при необходимости подтверждать участников.

### Клубы и площадки

Места, где проходят игры.

Им важно:

- быть найденными игроками;
- показать расписание;
- показать адрес, рейтинг, описание и удобства;
- получать новых посетителей.

### Администраторы сервиса

Люди, которые модерируют контент.

Им важно:

- управлять играми;
- управлять площадками;
- модерировать объявления;
- скрывать неподходящий контент;
- управлять пользователями.

## Главная страница

Главная страница - ключевой маркетинговый и навигационный экран.

Она должна сразу объяснять:

- что это за сервис;
- какие есть направления;
- что можно найти игры, места и людей;
- что пользователь может создать свою игру.

### Структура главной страницы

1. Header.
2. Hero-блок.
3. Быстрые действия.
4. Выбор направления.
5. Ближайшие игры.
6. Клубы и площадки.
7. Поиск игроков / сбор группы.
8. Footer.

### Header

В header должны быть:

- логотип;
- навигация;
- поиск;
- кнопка входа;
- кнопка создания игры.

Пример навигации:

- Игры;
- Места;
- Люди;
- События;
- Сообщество;
- О проекте.

CTA:

- Войти;
- Создать игру.

### Hero-блок

Hero должен быть креативным и динамичным.

Базовая идея:

- первый экран занимает крупный слайдер;
- слайды имеют скошенную форму;
- активный слайд самый широкий, цветной и детальный;
- неактивные слайды узкие, приглушенные, серые или затемненные;
- визуально слайдер напоминает игровые промо-панели.

Основные слайды:

- Настолки;
- НРИ;
- Мафия;
- Сообщество;
- Турниры и лиги.

Активный слайд должен содержать:

- крупный заголовок;
- короткое описание;
- 2 CTA-кнопки:
  - Найти игру;
  - Создать игру / Создать стол.

Hero не должен быть статичным баннером. Он должен ощущаться как главная точка входа в разные игровые направления.

### Быстрые действия

Под hero должны быть быстрые карточки:

- Найти место;
- Найти игроков;
- Ближайшие игры;
- Карта сообщества.

Карточки должны вести в соответствующие разделы.

### Блок направлений

- Настолки;
- НРИ;
- Мафия.

Каждая карточка должна иметь:

- название;

- визуальный акцент;

## Использование Redwood CLI

Максимально использовать Redwood CLI.

Перед ручным созданием любого файла нужно проверить, может ли Redwood CLI создать его автоматически.

Если может - использовать CLI.

Не писать вручную:

- базовые CRUD-страницы;
- SDL;
- services;
- scaffold;
- layouts;
- pages;
- cells;
- Prisma migration SQL;
- auth boilerplate;

если это можно сделать через Redwood CLI.

Примеры ожидаемого подхода:

```bash
yarn rw --help
yarn rw g page Home /
yarn rw g layout Public
yarn rw g layout Account
yarn rw g layout Admin
yarn rw g cell UpcomingGames
yarn rw g scaffold Venue
yarn rw g scaffold GameSession
yarn rw g scaffold PlayerPost
```

Если в текущей версии RedwoodJS команда отличается, нужно сначала проверить доступные команды через:

```bash
yarn rw --help
yarn rw g --help
```

И только потом использовать актуальную команду.

## Работа с данными

Серверные данные должны идти через GraphQL, Services и Cells.

Не использовать Zustand как замену серверному состоянию.

В Zustand можно хранить только клиентское UI-состояние:

* активный hero-слайд;
* открытые/закрытые модалки;
* состояние mobile menu;
* локальные фильтры до применения;
* UI-настройки;
* временные значения интерфейса.

В Zustand нельзя хранить как основной источник истины:

* список игр;
* список площадок;
* текущего пользователя;
* записи на игры;
* участников;
* избранное;
* данные, которые должны приходить с сервера.

## GraphQL и Cells

Использовать Redwood Cells для загрузки данных.

Cells нужны для:

* ближайших игр;
* списка игр;
* детальной страницы игры;
* списка площадок;
* детальной страницы площадки;
* объявлений игроков;
* моих игр;

Каждый Cell должен иметь стандартные состояния:

* Loading;

* Success.

## Права доступа

Правила:

* гость может смотреть публичные страницы;
* гость не может записываться на игры;
* гость не может создавать игры;
* авторизованный пользователь может создавать игры;
* пользователь может редактировать только свои игры;
* пользователь может отменять только свои записи;
* организатор может управлять участниками своей игры;
* админ может управлять всеми играми, площадками, объявлениями и пользователями.

## Валидация

Обязательная валидация:

* название игры обязательно;
* описание желательно, но не всегда обязательно;
* дата обязательна;
* время обязательно;
* maxPlayers должен быть больше 0;
* minPlayers не должен быть больше maxPlayers;
* нельзя записаться на отмененную игру;
* нельзя записаться на прошедшую игру;
* нельзя записаться дважды;
* нельзя записаться, если нет свободных мест;
* нельзя редактировать чужую игру;
* нельзя отменять чужую запись;
* email должен быть валидным;
* у площадки адрес необязателен; если его нет, адресный блок в UI скрывается;
* если игра офлайн, место или адрес должны быть указаны;
* если игра онлайн, должна быть указана информация для подключения или пометка, что организатор сообщит детали позже.

## Рабочий процесс

Рекомендуемый порядок реализации:

1. Создать Redwood-проект через CLI.
2. Настроить PostgreSQL.
3. Настроить Tailwind.
4. Настроить Auth.
5. Описать Prisma schema.
6. Сделать миграцию.
7. Сгенерировать scaffold для основных сущностей.
8. Сгенерировать layouts.
9. Сгенерировать pages.
10. Сгенерировать cells.
11. Доработать services.
12. Доработать UI.
13. Добавить проверки прав.
14. Добавить валидацию.
15. Проверить линт, тесты и сборку.

## Команды проверки

Перед завершением задачи нужно запускать:

```bash
yarn rw lint
yarn rw test
yarn rw build
```

Если команда падает, нужно:

1. Прочитать ошибку.
2. Исправить причину.
3. Запустить повторно.
4. Не скрывать проблему.

## Нельзя делать

Нельзя:

* игнорировать Redwood conventions;
* писать свой Express/Nest backend внутри Redwood без необходимости;
* заменять GraphQL/Services прямыми REST-запросами без причины;
* хранить серверные данные в Zustand как источник истины;
* писать CRUD вручную, если его можно сгенерировать Redwood CLI;
* создавать хаотичную структуру папок;
* смешивать API-логику с React-компонентами;
* оставлять TODO вместо рабочей логики;
* оставлять неиспользуемые импорты;
* оставлять нерабочие формы;
* делать только статичную верстку там, где нужен реальный сценарий MVP.

## Можно делать

Можно:

* использовать Redwood scaffold как стартовую точку;
* дорабатывать сгенерированные страницы;
* создавать кастомные UI-компоненты;
* использовать Zustand для UI-состояния;
* использовать Tailwind для дизайна;
* добавлять небольшие seed-данные для локальной разработки;
* делать временные mock images/placeholders, если реальных изображений нет;
* улучшать UX, если это не ломает MVP.

## Seed-данные

Для локальной разработки желательно добавить seed-данные:

* несколько площадок;
* несколько игр;
* несколько пользователей;
* несколько объявлений поиска игроков.

Примеры площадок:

* Board Room;
* Лофт Героев;
* Meeple House;
* Кубик Рубика.

Примеры игр:

* Крылья;
* Подземелья и драконы;
* Мафия Classic;
* Покорение Марса;
* 7 Wonders Duel.

Данные должны быть демонстрационными.

## Definition of Done

Задача считается выполненной, если:

* функциональность работает;
* нет ошибок TypeScript;
* нет очевидных ошибок lint;
* сборка проходит;
* UI адаптивен;
* есть loading/empty/error states;
* защищенные маршруты действительно защищены;
* права доступа проверяются на серверной стороне;
* формы имеют базовую валидацию;
* код соответствует RedwoodJS-подходу;
* нет лишней самодельной архитектуры поверх Redwood.

## Фиксация изменений модели данных

Если в процессе разработки меняется структура данных, связи между сущностями или смысл полей, это обязательно должно быть зафиксировано в `AGENTS.md`.

Примеры изменений, которые нужно документировать:

- добавлена новая сущность;
- удалена сущность;
- изменено название сущности;
- добавлено, удалено или переименовано поле;
- изменен тип поля;
- изменена обязательность поля;
- изменены enum-значения;
- изменены связи между моделями;
- изменилась кардинальность связи, например `one-to-many` на `many-to-many`;
- изменились правила владения сущностью;
- изменились права доступа к сущности;
- изменилась бизнес-логика вокруг сущности.

При таком изменении нужно обновить:

1. Раздел с моделями данных.
2. Раздел с enum, если затронуты enum-значения.
3. Раздел с правами доступа, если изменилась логика владения или модерации.
4. Раздел с роутингом, если появились новые страницы.
5. Раздел с GraphQL/Cells/Services, если появились новые операции.
6. Definition of Done, если изменились критерии готовности.

Нельзя менять Prisma schema, GraphQL SDL, services или связи между моделями и оставлять `AGENTS.md` в старом состоянии.

`AGENTS.md` должен оставаться актуальным источником контекста для ИИ-агентов и разработчиков. Если фактическая реализация начала отличаться от описания в `AGENTS.md`, нужно либо привести код к описанию, либо обновить `AGENTS.md`.
